# Setting up a project workspace

A workspace is one folder `C:\code\<project>` holding a **root repo** (documentation only) plus the
company's application repos cloned next to or inside it. The Dev Manager, the design workflow and
every agent find a project through this layout, so it must be the same shape every time.

## Target shape

```
C:\code\<project>\                       root repo (GitHub: <org>/<project>-agent-root or ai-root - ask)
├── CLAUDE.md                            what the project is, every repo's role + base branch, rules
├── README.md                            human onboarding: tree, prerequisites, clone commands, run, environments, housekeeping
├── .gitignore                           every sibling repo + compose base excluded (they are repos, not submodules)
├── knowledge-base/                      README (rules + index), glossary, architecture/{system-overview,api,frontends,deployment}, decisions/ADR-*, domains/*
├── design/                              README (method), PROJECT (specifics), STATUS, CHECKLIST
├── <frontend-repo>/ …                   siblings: Nuxt/Vue/React apps, Strapi, Flutter, static sites
├── <java-backend-repo>/                 sibling: Spring Boot / Gradle backend (runs against the shared sidecars)
└── docker-<project>-local/              compose base for PHP/Flow backends - the distribution and its packages are NESTED here:
    └── docker/web/<service>/<distribution>/Packages/Application/<Package>/
```

Deliverables of a setup, in order: (1) inventory, (2) layout decision per backend, (3) clones,
(4) root repo scaffold + knowledge base from a read-only analysis, (5) `companies.json` entry,
(6) skill scope `venture-labs/<project>` with a `<project>-context` skill, (7) Notion database
"Feature ideas · <Company>" seeded with findings, (8) summary + open questions for Christian.
Never push to any live repo's `main`/`dev`; the root repo is pushed only after Christian names it.

## Step 1 — inventory before anything else

- `gh repo list <org> --limit 100` and read **every** repo's manifest before cloning:
  `composer.json` (PHP: is it a *package* — `type: neos-package` — or a *distribution* — a root with
  `Web/`, `flow`, `require` on the org's packages?), `package.json`, `build.gradle`/`pom.xml`,
  `Dockerfile`, `docker-compose*.yml`, `cloudbuild*.yaml`, `kubernetes*.yaml`.
- Classify each repo: **package** (code), **distribution** (composer root that pins packages),
  **compose base** (`docker-<x>-local`: runs the distribution locally), **container/infra**
  (`docker-<x>-dev|live`: Dockerfile + Cloud Build + k8s + runtime `Configuration/`), **frontend**,
  **CMS**, **mobile**, **dead/reference**.
- Check what is deployed (GCP: GKE workloads, URL maps, DNS, Cloud Build triggers) — the repos
  alone lie about what is live.

## Step 2 — decide the layout per backend (the rule that was missed on 2026-09-06)

| Backend stack | Layout | Why |
|---|---|---|
| **Neos Flow / composer distribution + compose base** (MachineMaster, Tap2Link, honey, Bienenwanderung) | **Nested**: `docker-<x>-local/docker/web/<service>/<distribution>/Packages/Application/<Package>` — one `<service>` folder per compose service (read the `volumes:` of `docker-compose.yml` for the exact folder names), the distribution repo cloned there, and **every package the distribution's `composer.json` requires from the org** cloned under `Packages/Application/` as git working copies (add a `composer` remote = origin; composer's own source install uses that name) | the container bind-mounts the distribution's `Packages/`, so only a package inside it is what the container runs and tests |
| Live distributions / live containers (`*-flow-live`, `bee-flow`, `docker-*-live`) | siblings, reference only — never run, never pushed | they pin what is deployed |
| **Java / Spring Boot** (Loop Studio) | sibling; runs natively or in its own compose against the shared sidecars `C:\code\docker-sidecars` (`services_network`: MySQL, Redis, Elasticsearch); local properties generated by a prepare script | no distribution concept — the repo is the deployable |
| Node/Nuxt/Vue frontends, static sites, Strapi, TypeScript backends, Flutter | siblings | self-contained repos |
| Strapi with its own compose | sibling; runs in its own compose on `services_network` | |

Write the decision into the root `README.md` (tree + backend section) and `CLAUDE.md` (repo list),
and mirror the paths in `companies.json`. If a compose base's `.gitignore` does not ignore the
nested distribution folder, add it to that repo's `.git/info/exclude` (local, no commit).

## Step 3 — clone

- Every repo in the org that is live or referenced by a live one; dead ones only if they explain
  something (say so in `CLAUDE.md` as "reference only").
- Check out the **real** working branch (read `cloudbuild*.yaml` triggers and the live distribution's
  `composer.lock`): the GitHub default branch can be dead code (Tap2Link: `dev2`).
- Clone with SSH; never clone into a path with spaces.

## Steps 4–8 — what to produce

- **Root repo**: `.gitignore` first (list every sibling and compose-base folder so an accidental
  `git add -A` never swallows a repo), then `CLAUDE.md`, `README.md`, `knowledge-base/`
  (`README.md` with the folder rules + a complete index; every doc ends with `## Related`),
  `design/`. Commit locally; push only to the repo Christian names.
- **Knowledge base** from read-only analysis agents (backend + infra, frontends, one per odd repo)
  plus the GCP inventory: system overview, api, frontends, deployment, 3–4 ADRs for decisions the
  code will not explain (incl. what is *parked* on purpose), one doc per business domain, glossary
  (code ↔ UI ↔ German). Record every committed secret **by path only**, never by value.
- **`agents/dev-manager/companies.json`**: one entry per project; repo paths = the nested paths for
  Flow packages; `build`/`test` commands that run on this machine or an honest `echo "not run: …"`;
  `denyPaths` for env/cloudbuild/k8s/compose/`files/`/`Configuration/Settings.yaml`/keys.
- **Skill scope** `C:\ai\skills\venture-labs\<project>\` with `.claude-plugin/plugin.json` +
  `skills/<project>-context/SKILL.md` (what it is, technical shape, rules, where things are);
  commit + push in the venture-labs repo; marketplace entry in the skills root.
- **Notion**: "Feature ideas · <Company>" (Dev Manager ideas schema) seeded with the findings
  (secrets, security gaps, dead deployments, branch traps, missing tests, local setup, decisions).
- **Summary** for Christian: what exists, questions/decisions, what did not work — into the
  morning-review doc or the plan doc, and CORE_MEMORY.

## Worked example — MachineMaster (proven 2026-09-05)

```
C:\code\machinemaster\
├── customer-frontend/ global-platform-frontend/ retailer-frontend/ admin-frontend/ retailer-landing-page/ moerschen-cms/   siblings
└── docker-moerschen-local/                                   compose base
    └── docker/web/moerschen-flow-dev/                        distribution (gitignored by the base repo)
        ├── Configuration/Settings.yaml                       local settings, gitignored
        └── Packages/Application/Moerschen.Main/              the package - work HERE (branch dev, remote composer = origin)
```
`composer install` runs inside the private PHP base image with a host-side mirror cache of the
private packages mounted in (no SSH key inside the container) and `preferred-install … source` so
the org's packages become git working copies — the exact commands, the port-override rule, the
`Routes.yaml` and gitlink gotchas and the PHPUnit baseline for the Dev Manager are in
`references/flow-backend-nesting.md`; `C:\code\honey-analysis\README.md` §3 is the full proven run
(2026-09-06), `C:\code\machinemaster\README.md` §4 the earlier one.

## Never

- Clone a Flow package as a sibling "for now" — it is what this skill exists to prevent.
- Copy a knowledge-base index or design README from another project without rewriting it.
- Put secret values, customer data or personal data into any workspace doc, spec, Slack or Notion.
- Push root repos, cut DNS over, or create GitHub repos without Christian's word.
